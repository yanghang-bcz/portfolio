## 2. 各阶段结果

### 阶段一 · 分级加载（`90ad4cc`）

- 首页 15 个 `<img>` 保持真实 `src`；其余 24 个改成 `data-src`，栏目首次 `.is-active` 时取。
- 断言：首屏资源里 **0 个** `assets/music/*` / `assets/travel/*`；进入 Music 后 16 张封面**各只请求一次**。
- 视觉：0 处几何/排版差异（14 处 `naturalSize 0×0 → 实际值` 是懒加载图此前没被触发，属预期）。

### 阶段二 · AVIF / WebP（`78df309`）

- 53 张图逐图定质量：AVIF q45–q85，四道 SSIM 门槛（显示尺寸 ≥0.995 / 2× ≥0.980 / 3× ≥0.960 / 1:1 ≥0.93）。
- 首页走 `<picture>`（不依赖 JS），内页走 `img[data-avif]` —— 因为 `<picture>` 在 flex 里即使 `display:contents` 也会白吃一个 `gap`，实测让 About 四个标签整体右移 12 px。
- 体积：home 0.916 / music 0.204 / travel 0.525 / about 0.177 = **1.82 MB**。
- 内页目标像素按**真实视觉尺寸**（祖先链 transform 行列式开方）重算，Music 封面与 Travel 缩略图从「手机端只有 0.74×」回到 1:1。

### 阶段三 · 字体子集化（`a28ede7`）

- `2 242 408 B → 431 904 B（−80.7%）`，保留 798 码位。
- 逐字比对前进宽度：835 个字符 **0 差异**。
- 43 个字仍走系统回退（日文假名、勝娠檎爾獗紙葉設訴達還、emoji、©ãö↓✕）——它们本来就不在原始字体里，行为未变，没有为子集化凭空补字形。

### 阶段四 · 开屏与 Loading（`e3c3b60`）

按评审意见实现的三条规则：

1. **出现即可点。** 按钮没有 `disabled`，没有"全部下完才解锁"。断言是在**挂载那一瞬**（13 张图一张都还没回来）点下去，必须生效。
2. **没就绪就点 → 原地 Loading...。** 位置尺寸不动，继续加载，就绪后自动进，不要第二次点击。1.5 Mbps 下实测：等 8.83 s，然后自己进去。
3. **就绪再点 → 当场进。** `leave()` 在动画开始前就撤掉命中区域、解开 `body` 滚动、把焦点交回 `#page-content`；退场只是一段视觉收尾，**不占等待**（实测 0.1 ms）。已经等过的那一类干脆不播退场。
4. **失败不锁门。** 图片 500/1500/3500 ms 三次重试，字体同样；单任务 20 s 上限；报过错的图再等 6.5 s 就放弃。实测掐断 `mac.avif`：4 次请求后放弃，开屏自己放行。

途中修掉的真问题：

- **预载从"抢"改成"等"。** 一开始开屏自己 `new Image()` 预拉 13 张图，结果 13 个低优先级请求占满 HTTP/1.1 的 6 条连接，六个 `defer` 脚本被挤到 8.2 s 才回来（阶段三只要 0.5–1 s）。改成只监听页面自己那几个 `<img>` 的 `load`+`decode`，一个字节都不多发。
- **进度条不会一开屏就写 100%。** 任务清单在挂载前登记，图片任务要等 `DOMContentLoaded` 才知道是哪几张，因此加了一道 `imagesQueued` 闸门。
- **390 px 的孤字。** 副标题原会把"里"单独留在第三行；中文那行拆成独立块走 `text-wrap: balance`。
- **焦点态不再整体反色。** 按钮一出现就 `focus()`，用反色做焦点态会让首屏永远是深色块；改用站点既有的虚线描边，等待态只剩一圈虚线框。

## 3. 冷缓存性能（1.5 Mbps / 150 ms RTT / gzip / 缓存禁用）

口径很重要，三个数必须分开看：

| 口径 | 含义 | 阶段三 | 阶段四 |
|---|---|---|---|
| **① 首页阶段** | 打开首页到"能看能点"实际传输 | 1764 KiB / 27 请求 | **1764 KiB / 27 请求** |
| **② 完整资源** | 再把六个栏目都走一遍 | 2660 KiB / 67 请求 | **2660 KiB / 67 请求** |
| **③ 点 ENTER 后的等待** | 点下 → 首页可用 | 无此概念 | 就绪点 0.1 ms / 落地就点 8.83 s |

① 的构成（阶段四）：

| 类别 | 体积 | 明细 |
|---|---|---|
| 图片 | 1038.9 KiB (14) | 首页 13 张 AVIF + `paper.webp` |
| 字体 | **679.0 KiB (6)** | HuiwenMincho 422.1 · SpecialElite 162.6 · IMFell 58.8 · Architects 13.1 · Oswald 12.8 · SpaceMono 9.6 |
| HTML | 18.7 KiB | gzip 后（原文件 53.1 KiB，含内联开屏） |
| JS | 15.9 KiB (5) | |
| CSS | 11.1 KiB (1) | |

### 关于报告里的 1.40 MB / 3.64 MB

重新按"一次真实访问实际传输"量，得到的是 **1.72 MiB（首页阶段）/ 2.60 MiB（全站）**，
对不上原报告的 1.40 / 3.64。两个数差在哪：

- **首页阶段多出的约 0.33 MiB 就是字体。** 原口径只算了汇文明朝（431 KB），
  但实际上**首屏加载了 6 个字体**（679 KB）：Special Elite 162 KB，以及内页那四个
  拉丁字体 95 KB —— 因为六个栏目都在 DOM 里（只是 `visibility:hidden`），
  它们的文字仍然触发字体下载。这是本轮比原报告更准确的一处。
- **全站的 3.64 MB 更像"素材总体积"口径**：AVIF 1.81 MB + WebP 2.49 MB = 4.30 MB，
  或者把 fallback 一起算进去；而一次真实访问只会走其中一种格式（2.60 MiB）。

### ENTER 的真实等待（1.5 Mbps）

```
开屏上屏 625 ms  |  第一帧内容 744 ms  |  资源齐 9535 ms
A 落地就点：707 ms 点下去 → 9535 ms 进站   ★ 等 8.83 s（期间是进度条，不是白屏）
B 就绪才点：9563 ms 点下去 → 9563 ms 进站   ★ 等 0.1 ms
```

首页那 1.72 MiB 在 1.5 Mbps 下就是要 9.5 秒，这一点阶段三阶段四一样；
区别只在于这 9.5 秒是"进度条 + 装订中"还是"首页一块块长出来"。
